# Архитектура и текущее состояние VPN-бота

Документ описывает рабочую архитектуру проекта на 22 августа 2026 года. Здесь намеренно нет публичных IP-адресов, паролей, Telegram-токена, приватных SSH-ключей, fingerprint и содержимого пользовательских `.ovpn`.

## 1. Назначение системы

Telegram-бот выпускает и обслуживает OpenVPN-конфиги, хранит пользователей и сроки действия, собирает трафик, отправляет напоминания и позволяет администратору управлять VPN-серверами.

Особенность текущей схемы — российский сервер является единой точкой входа и управления, но пользовательский VPN-трафик выходит в интернет через отдельный зарубежный VPN-сервер. Это позволяет клиентам подключаться к российскому адресу, не меняя адрес выхода VPN.

```text
Пользователь OpenVPN
        │ TCP к российской точке входа
        ▼
Российский control/relay-сервер
        │ обратный SSH port-forward
        ▼
Зарубежный VPN exit-сервер
        │ NAT
        ▼
Интернет

Telegram API ◄── SOCKS через VPN exit ◄── Telegram-бот на RU-сервере
VPN exit SSH  ◄── отдельный SOCKS-туннель ◄── Telegram-бот на RU-сервере
```

## 2. Роли серверов

### 2.1. Российский control/relay-сервер

Это основной сервер системы. На нём находятся:

- рабочая копия приложения: `/opt/vpnbot/app`;
- Docker Compose-проект с ботом и PostgreSQL;
- рабочая `.env`: `/opt/vpnbot/app/.env`;
- секреты контейнера: `/opt/vpnbot/app/secrets`;
- датированные резервные копии: `/root/vpnbot-backups/<UTC timestamp>`;
- непривилегированный системный пользователь `vpn-relay` для обратных SSH-туннелей;
- разрешённые relay-ключи: `/var/lib/vpn-relay/.ssh/authorized_keys`;
- публичная TCP-точка входа OpenVPN;
- внутренние SOCKS-точки для Telegram и управляющего SSH.

Docker Compose запускает два постоянных контейнера:

| Контейнер | Назначение |
| --- | --- |
| `app-bot-1` | Node.js/TypeScript Telegram-бот, фоновые задания и управление VPN-серверами |
| `app-postgres-1` | PostgreSQL 17, единственная рабочая БД проекта |

Оба контейнера используют внешнюю Docker-сеть `vpnbot`. Она создаётся отдельно и не удаляется при обычном `docker compose down`.

Публичный стандартный порт OpenVPN на RU-сервере обслуживается системным socket-proxy. Он передаёт соединение на локальный reverse-forward текущего VPN exit-сервера. Для новых VPN-серверов бот выделяет отдельные публичные TCP-порты из настроенного диапазона.

### 2.2. Активный зарубежный VPN exit-сервер

Сейчас это единственный включённый VPN-сервер в БД, его ключ — `srv_1`. На нём работают:

- OpenVPN Server;
- `/etc/openvpn/server/server.conf`;
- PKI EasyRSA в `/etc/openvpn/server/easy-rsa`;
- ограниченный helper `/usr/local/sbin/openvpn-bot-helper`;
- disconnect-hook `/usr/local/sbin/openvpn-traffic-disconnect`;
- очередь завершённых сессий `/var/lib/openvpn-bot/traffic-events`;
- пользователь `vpn-bot` для управляющих операций;
- постоянные reverse SSH-туннели на RU-сервер.

Для текущего, настроенного вручную сервера reverse SSH разделён на три systemd-сервиса:

| Сервис | Назначение |
| --- | --- |
| `vpn-relay-tunnel.service` | Доставка публичного OpenVPN TCP с RU-сервера на OpenVPN exit |
| `vpn-telegram-tunnel.service` | SOCKS для запросов Telegram Bot API |
| `vpn-control-tunnel.service` | Отдельный SOCKS для управляющего SSH и резервный SSH-forward |

Разделение Telegram и управляющего SSH сделано намеренно: сбой или зависание одного туннеля не должен останавливать другой.

### 2.3. Удалённые и исторические серверы

Два прежних сервера удалены из пула через админ-панель. Бот больше не использует их для выпуска, скачивания, статистики или SSH-операций.

В PostgreSQL могут сохраняться исторические `server_key` удалённых серверов у просроченных и отозванных конфигов. Это нормально: записи нужны для истории, но не считаются доступными серверами. Действующих конфигов без сервера сейчас нет.

Если просроченный конфиг с историческим `server_key` продлить, бот создаст новый сертификат на доступном сервере и заменит техническое имя и `server_key`.

## 3. Сетевые потоки

### 3.1. OpenVPN пользователя

1. Пользователь получает `.ovpn` от бота.
2. В `remote` указан российский relay и порт конкретного VPN-сервера.
3. RU-сервер принимает TCP-соединение.
4. Reverse SSH-forward доставляет соединение на OpenVPN exit.
5. OpenVPN exit расшифровывает трафик и выполняет NAT в интернет.
6. Внешние сайты видят адрес VPN exit, кроме адресов и доменов из белого списка.

Текущий `srv_1` использует основной relay-порт. Автоматически добавленные серверы получают уникальный `relay_port` из диапазона `VPN_RELAY_PORT_START`–`VPN_RELAY_PORT_END`.

### 3.2. Telegram

Бот работает на российском сервере, но `api.telegram.org` вызывается через `TELEGRAM_PROXY_URL`. SOCKS-туннель заканчивается на VPN exit, поэтому Telegram-трафик выходит через зарубежную сеть.

Используется `socks5h`: DNS-имя Telegram разрешается на стороне SOCKS, а не российским хостом.

### 3.3. Управляющий SSH

Команды helper к VPN-серверам идут через отдельный `SSH_PROXY_URL`. Бот проверяет SSH host fingerprint и не принимает неизвестный или изменившийся host key.

Root-пароль нужен только при первичной автоматической настройке нового VPS. Он передаётся в SSH-сессию один раз и не записывается в `.env`, PostgreSQL или логи приложения.

После bootstrap бот работает через пользователя `vpn-bot` и сгенерированный отдельный ключ. Приватный управляющий ключ хранится в записи VPN-сервера в PostgreSQL, поэтому дампы БД являются секретными.

## 5. PostgreSQL

PostgreSQL на RU-сервере — единственный источник истины. На VPN exit локальной БД нет.

Основные сущности:

| Таблица/модель | Содержимое |
| --- | --- |
| `users` | Telegram ID, username и имя пользователя |
| `vpn_configs` | конфиг, техническое имя сертификата, сервер, срок и статус |
| `client_names` | глобальная резервация уникальных имён OpenVPN-клиентов |
| `vpn_servers` | серверы, SSH-доступ, статус, `relay_port` и признак управляемого relay |
| `legacy_clients` | найденные на сервере старые сертификаты и их привязка |
| `notifications` | защита от повторных напоминаний |
| `pending_revocations` | отложенный отзыв старого сертификата после перевыпуска |
| `traffic_events` | завершённые VPN-сессии и байты |
| `bypass_domains` | белый список доменов из админ-панели |

Связь `vpn_configs.server_key` намеренно не оформлена внешним ключом на `vpn_servers`: после удаления VPS исторические конфиги и трафик должны сохраниться.

## 6. Жизненный цикл VPN-конфига

### Выпуск

1. Бот выбирает готовый и включённый сервер с наименьшим числом действующих клиентов.
2. Резервирует случайное 12-символьное техническое имя.
3. Через helper создаёт сертификат OpenVPN.
4. Записывает конфиг в PostgreSQL.
5. Подменяет `remote` на российский relay и порт выбранного сервера.
6. Добавляет правила белого списка и блокировку IPv6.
7. Отправляет `.ovpn` пользователю.

### Повторное скачивание

Файл собирается заново из актуального сертификата. Поэтому изменения relay, IP/CIDR или белых доменов начинают действовать после повторного скачивания без замены сертификата.

### Перевыпуск

Создаётся новый сертификат. Старый остаётся рабочим примерно пять минут и затем отзывается фоновой задачей. Это даёт пользователю короткое окно для замены файла.

### Принудительный перенос

Создаётся сертификат на целевом сервере, запись БД переключается на него, а старый сертификат отзывается сразу. Если исходный сервер уже удалён, перенос не откатывается: старый сервер недоступен, поэтому новый сертификат считается единственным рабочим.

### Истечение срока

Каждый час на пятой минуте бот отзывает сертификаты, срок которых закончился, и помечает их как `expired`. Просроченный конфиг остаётся видимым ограниченное время согласно `hidden_at`.

### Продление

- действующий конфиг сохраняет сертификат и получает новый срок;
- просроченный или ранее отозванный конфиг получает новый сертификат на доступном сервере;
- массовое продление изменяет только действующие, неотозванные конфиги.

## 7. Преобразование `.ovpn`

Перед каждой выдачей `src/vpn-profile.ts`:

1. заменяет исходный `remote` на российский relay;
2. использует индивидуальный `relay_port` сервера;
3. добавляет `block-ipv6`, если включён `VPN_BLOCK_IPV6`;
4. добавляет маршруты `VPN_BYPASS_ROUTES` через `net_gateway`;
5. добавляет домены из `VPN_BYPASS_DOMAINS` и таблицы `bypass_domains` через `net_gateway`.

Маршрут `net_gateway` отправляет трафик через исходный шлюз устройства. Для белых IP и доменов сайт видит реальный IP пользователя, а не VPN exit.

Ограничения белых доменов:

- `example.com` и `www.example.com` — разные записи;
- wildcard-домены не поддерживаются маршрутизацией OpenVPN;
- DNS разрешается при подключении;
- при смене адресов CDN может потребоваться переподключение;
- изменение списка требует повторного скачивания существующего профиля;
- kill switch конкретного OpenVPN-клиента может запрещать обходящие маршруты.

## 8. Управление серверами

### Автоматическое добавление

Администратор передаёт боту адрес, SSH-порт, одноразовый root-пароль и отображаемое название.

Bootstrap:

1. создаёт запись `pending` с выключенной выдачей;
2. выделяет уникальный `srv_N` и relay-порт;
3. подключается по root через управляющий SOCKS;
4. устанавливает OpenVPN/TCP неинтерактивным установщиком;
5. устанавливает helper и traffic hook;
6. создаёт пользователя `vpn-bot` и отдельный SSH-ключ;
7. устанавливает reverse tunnel unit `vpnbot-relay-tunnel.service`;
8. проверяет локальный OpenVPN и публичный relay-порт;
9. сохраняет SSH host fingerprint и управляющий ключ;
10. только после успешных проверок ставит `ready` и включает выдачу.

Новые серверы используют локальный OpenVPN TCP-порт и отдельный публичный порт RU relay. Один российский IP таким образом обслуживает несколько VPN exit-серверов.

### Удаление

Для автоматически добавленного сервера бот сначала останавливает управляемый reverse tunnel, затем удаляет сервер, legacy-клиентов и его ожидающие отзывы из БД. Пользовательские конфиги и история трафика сохраняются.

Конфиг с удалённого сервера можно перенести на действующий сервер. Старый сертификат отозвать невозможно, но он недоступен вместе с удалённым сервером, поэтому перенос завершается без отката.

### Ограничения доступа

- `vpn-bot` имеет `sudo` только на helper и остановку своего relay unit;
- `vpn-relay` не получает обычную shell-сессию;
- relay authorized key ограничен port-forwarding и forced command;
- SSH host keys проверяются по fingerprint/known_hosts;
- root-пароль не сохраняется.

## 9. Трафик и статистика

OpenVPN status-файл используется для активных сессий. Disconnect-hook записывает завершённые сессии в очередь на VPN exit. Бот раз в минуту:

1. читает активные и завершённые сессии через helper;
2. импортирует завершённые события идемпотентно по составному ключу;
3. связывает события с конфигами по `server_key` и `client_name`;
4. показывает накопительный upload/download и подключения «сейчас».

Исторический трафик сохраняется даже после удаления сервера или конфига.

## 10. Фоновые задания

| Период | Задание |
| --- | --- |
| При старте и ежедневно в `REMINDER_HOUR` | Напоминания за 3, 2 и 1 день до окончания |
| При старте и каждый час на пятой минуте | Отзыв просроченных сертификатов |
| При старте и каждую минуту | Импорт трафика |
| При старте и каждую минуту | Отложенный отзыв сертификатов после перевыпуска |

Для каждого типа задания есть in-process lock, поэтому следующий запуск не начинает второй экземпляр, пока предыдущий не завершился.

## 12. Текущее состояние production

На момент последней проверки:

- один сервер `srv_1` имеет статус `ready` и включён;

- 46 конфигов были массово перевыпущены после удаления старых серверов;

- несколько просроченных/отозванных записей старых серверов сохранены как история;
- бот и PostgreSQL находятся в состоянии `Up`, PostgreSQL проходит healthcheck;
- текущий профиль использует российскую точку входа, а сертификат и NAT — активный VPN exit;
- полный набор — 45 автоматических тестов — проходит.

## 13. Резервные копии и восстановление

Перед изменениями production создаётся каталог:

```text
/root/vpnbot-backups/<UTC timestamp>/
```

Логический дамп:

```bash
cd /opt/vpnbot/app
mkdir -p backups
docker compose exec -T postgres \
  pg_dump -U vpnbot -d vpnbot -Fc > backups/vpnbot.dump
sha256sum backups/vpnbot.dump
```

Восстановление сначала выполняется на отдельной тестовой БД. Для аварийного восстановления production бот следует остановить, восстановить дамп в PostgreSQL, выполнить миграции той же версии исходного кода и только затем запустить бот.

Дамп содержит персональные данные, SSH-ключи серверов и состояние сертификатов, поэтому его нельзя добавлять в Git или передавать как обычный файл.

## 14. Проверка и развёртывание

Локально перед публикацией:

```bash
npm ci
npm run typecheck
npm test
git diff --check
```

На production:

```bash
cd /opt/vpnbot/app
docker compose config -q
docker compose up -d --build bot
docker compose ps
docker compose logs --tail=100 bot
```

Контейнер бота сам выполняет `prisma migrate deploy`. Для рискованных изменений сначала поднимается временный PostgreSQL из `compose.test.yaml`, применяются все миграции с нуля и выполняются тесты. Тестовый контейнер и образ после проверки удаляются.

Исходный Git-репозиторий является канонической версией кода. `/opt/vpnbot/app` на production — развёрнутая рабочая копия; изменения сначала фиксируются в Git, а не редактируются как единственный экземпляр непосредственно на сервере.

## 15. Диагностика

### Состояние контейнеров

```bash
cd /opt/vpnbot/app
docker compose ps
docker compose logs --tail=100 bot
```

### Состояние OpenVPN exit

```bash
systemctl status openvpn-server@server.service
systemctl status vpn-relay-tunnel.service
systemctl status vpn-telegram-tunnel.service
systemctl status vpn-control-tunnel.service
```

Для автоматически добавленного сервера имя relay unit — `vpnbot-relay-tunnel.service`.

### Типовые симптомы

| Симптом | Что проверять |
| --- | --- |
| Бот не отвечает | контейнер bot, Telegram SOCKS, Telegram reverse tunnel |
| Не создаётся сертификат | SSH proxy, fingerprint, helper, EasyRSA |
| VPN подключается без интернета | `net.ipv4.ip_forward`, NAT/iptables, DNS push |
| VPN не подключается | публичный relay-порт, reverse tunnel, OpenVPN TCP |
| Не переносится старый конфиг | доступность целевого сервера; удалённый исходный сервер больше не должен блокировать перенос |
| Не работает белый домен | точное имя, повторное скачивание, DNS/CDN, kill switch клиента |
| Нет live-статистики | OpenVPN status-файл, helper и управляющий SSH |

## 16. Известные ограничения и дальнейшие улучшения

- Чистый OpenVPN маршрутизирует домены через DNS-результат на момент подключения, а не по имени каждого HTTP-запроса.
- Один российский IP обслуживает несколько VPN exit через разные TCP-порты; некоторые клиентские сети могут разрешать только стандартные порты.
- Управляющие SSH private keys хранятся в PostgreSQL без отдельного прикладного шифрования at rest.
- Автоматические VPS используют общий ограниченный relay tunnel key. Ограничения `authorized_keys` уменьшают последствия утечки, но для крупной инфраструктуры лучше выпускать уникальный relay key на каждый сервер через отдельный provisioning API.
- Production-развёртывание сейчас выполняется вручную; CI/CD и автоматическая проверка после deploy пока отсутствуют.
- Высокая доступность PostgreSQL и RU relay пока не настроена: российский control-сервер остаётся единой точкой отказа.

## 17. Правила безопасности

Никогда не коммитить:

- `.env`;
- root-пароли;
- Telegram Bot Token;
- `DATABASE_URL` с паролем;
- приватные SSH-ключи;
- содержимое `secrets/`;
- дампы БД;
- `.ovpn`, сертификаты и PKI.

После передачи доступа root-пароли меняет владелец инфраструктуры. Рабочие операции бота не должны зависеть от root-пароля после bootstrap.
