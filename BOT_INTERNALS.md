# Внутреннее устройство VPN-бота

Документ описывает приложение, его данные и пользовательские сценарии в состоянии на 26 августа 2026 года. Серверная установка, сетевые маршруты и пошаговое развёртывание вынесены в [SERVER_INFRASTRUCTURE.md](SERVER_INFRASTRUCTURE.md).

В репозитории и в этом документе намеренно нет рабочих паролей, токена Telegram, приватных ключей, SSH fingerprint и публичных IP production-серверов.

## 1. Назначение и границы приложения

Бот является панелью управления OpenVPN, а не самим VPN-сервером. Он:

- регистрирует Telegram-пользователей;
- выпускает, перевыпускает, переносит и отзывает клиентские сертификаты;
- хранит владельца, название и срок действия каждого конфига;
- формирует `.ovpn` по запросу и отправляет его в Telegram;
- показывает накопленный трафик и признак активного подключения;
- напоминает об окончании срока и автоматически отзывает просроченные сертификаты;
- управляет пулом VPN-серверов и позволяет добавлять сервер по SSH;
- предоставляет администратору поиск, статистику, массовое продление и рассылки.

Бот не хранит готовые `.ovpn` в PostgreSQL или внутри контейнера. Профиль каждый раз экспортируется с нужного OpenVPN-сервера, после чего его публичный endpoint нормализуется перед отправкой.

## 2. Общая схема приложения

```text
Telegram-пользователь
        │ Bot API
        ▼
grammY / src/bot.ts
        │
        ├── ConfigService ─────────────┐
        ├── ServerManager ─────────────┤
        ├── TrafficService ────────────┼── Prisma ── PostgreSQL
        ├── BroadcastService ──────────┤
        └── BackgroundJobs ────────────┘
                    │
                    ▼
           OpenVpnGateway / SSH2
                    │ отдельный vpn-bot + sudo helper
                    ▼
          EasyRSA, CRL, OpenVPN status и traffic events
```

Основной процесс — один Node.js-процесс. Очереди вынесены не в отдельный брокер, а представлены таблицами PostgreSQL и периодическими фоновыми заданиями. Поэтому PostgreSQL является единственным обязательным состоянием приложения.

## 3. Технологический стек и структура кода

- Node.js 22, TypeScript и ESM;
- grammY для Telegram Bot API;
- Prisma ORM 7 и PostgreSQL 17;
- SSH2 для управляющих SSH-соединений;
- SOCKS-прокси для Telegram и SSH из российской сети;
- Luxon для дат в заданном часовом поясе;
- node-cron для периодических заданий;
- Docker Compose для production и отдельного интеграционного PostgreSQL.

## 4. Запуск процесса

`src/index.ts` выполняет запуск в следующем порядке:

1. Загружает и валидирует `.env`.
2. Создаёт подключение к PostgreSQL.
3. Собирает `OpenVpnGateway`, `ServerManager`, `ConfigService` и `TrafficService`.
4. Синхронизирует с БД серверы, заданные через переменные окружения.
5. Создаёт grammY-бота и регистрирует команду `/start`.
6. Запускает фоновые задания; задания, для которых это важно, также выполняются один раз сразу.
7. Запускает long polling только для `message` и `callback_query`.
8. На `SIGINT`/`SIGTERM` останавливает polling, задания и соединение с БД.

Перед Node.js-командой контейнер выполняет `prisma migrate deploy`. Новая версия приложения не должна стартовать с неприменённой схемой.

Если задан `TELEGRAM_PROXY_URL`, только HTTP-запросы Telegram Bot API выполняются через `SocksProxyAgent`. Если задан `SSH_PROXY_URL`, управляющие SSH-соединения идут через отдельный SOCKS5-прокси. Эти каналы специально разделены.

## 5. Модель данных

Актуальная схема находится в `prisma/schema.prisma`, а история изменений — в `prisma/migrations`.

| Модель | Что хранит |
| --- | --- |
| `User` | Telegram ID, username и данные пользователя |
| `VpnConfig` | владелец, отображаемое и техническое имя, сервер, срок и статус |
| `ConfigRequest` | пользовательская заявка, её состояние и выданный по ней конфиг |
| `ClientName` | все технические имена, когда-либо связанные с конфигом |
| `VpnServer` | сервер пула, SSH-реквизиты, relay-порт, состояние и доступность выдачи |
| `TrafficEvent` | завершённые сессии и байты; ключ включает сервер и ID события |
| `PendingRevocation` | очередь гарантированного отложенного отзыва старого сертификата |
| `Notification` | защита от повторной отправки напоминаний |
| `LegacyClient` | привязка ранее созданного вручную OpenVPN-клиента |

Принципиальные решения схемы:

- `VpnConfig.serverKey` и `TrafficEvent.serverKey` не имеют внешнего ключа на `VpnServer`. Удаление сервера из пула не стирает конфиги и историю.
- Технические имена глобально резервируются в `ClientName`, поэтому случайное повторное использование имени после переноса невозможно.
- Частичный уникальный индекс разрешает пользователю только одну заявку в состоянии `pending` или `processing`.
- Событие трафика уникально по паре «сервер + ID события», что делает повторный импорт идемпотентным.
- В `VpnServer` хранится приватный управляющий SSH-ключ. Дамп БД считается секретом того же уровня, что и файл ключа.

Статусы конфига:

- `active` — сертификат действует и срок ещё не закончился;
- `expired` — срок закончился, но профиль может оставаться видимым;
- `revoked` — сертификат присутствует в CRL;
- `error` — операция не завершилась штатно и требует внимания.

Статусы сервера:

- `pending` — автоматическая настройка ещё выполняется;
- `ready` — helper доступен и сервер пригоден к работе;
- `error` — настройка или контрольная проверка завершилась ошибкой.

Отдельный флаг разрешает приостановить новую выдачу, не удаляя сервер и не ломая существующие профили.

## 6. Даты и жизненный цикл конфига

Пользовательская дата окончания трактуется как конец указанного дня в `TIMEZONE`, по умолчанию `Europe/Moscow`.

```text
выдача ── active ── точный expiresAt ── expired
                                      │
                                      ├── +24 часа: отзыв сертификата
                                      └── +10 дней: скрытие из списка пользователя
```

Массовое продление прибавляет выбранный интервал к индивидуальному текущему сроку каждого действующего конфига, а не отсчитывает общий срок от сегодняшнего дня. После изменения пересчитывается и `hiddenAt`.

### 6.1. Обычная выдача

1. Сервис выбирает пригодный сервер с минимальным числом действующих сертификатов.
2. Генерирует случайное техническое имя из 12 строчных латинских букв и резервирует его глобально; допускается до 100 попыток.
3. Через SSH вызывает helper `create`.
4. Только после успешного выпуска создаёт запись `VpnConfig`.
5. Если запись в БД не удалась, новый сертификат немедленно отзывается как компенсация.

При одинаковой нагрузке серверы сравниваются по стабильному ключу, поэтому выбор детерминирован.

### 6.2. Скачивание

Для пользователя доступны только активные и неистёкшие конфиги. Администратор может выгрузить существующий просроченный профиль, пока сертификат фактически не отозван.

Helper выполняет `download`, приложение преобразует профиль и отправляет его как документ. Файл существует только во время операции.

### 6.3. Пользовательский перевыпуск

Пользователь выбирает другой доступный сервер. Новый сертификат получает прежнее отображаемое название и срок. После переключения запись старого сертификата попадает в `PendingRevocation` с задержкой примерно пять минут. Фоновая задача повторяет отзыв при временной ошибке.

Это короткое окно позволяет скачать новый файл до остановки старого.

### 6.4. Административный перенос

Административный перенос рассчитан на немедленное переключение:

1. На целевом сервере выпускается новый сертификат.
2. БД переключается на новое техническое имя и сервер.
3. Старый сертификат отзывается сразу.
4. Если отзыв на доступном исходном сервере не удался, приложение возвращает запись к прежнему состоянию и отзывает только что созданный сертификат.

Если исходный сервер уже удалён из пула, перенос завершается без попытки обратиться к нему. Это позволяет восстановить «осиротевшие» записи после потери VPS.

### 6.5. Продление отозванного конфига

Отозванный сертификат нельзя сделать действующим удалением строки из CRL. Вместо этого создаётся новое техническое имя: сначала на прежнем доступном сервере, иначе на другом сервере пула.

### 6.6. Переименование и отзыв

Переименование меняет только безопасное отображаемое имя длиной 1–40 символов. CN сертификата не меняется. Отзыв обновляет CRL на сервере и статус в БД.

## 7. Формирование клиентского профиля

`src/vpn-profile.ts` получает экспортированный сервером профиль и:

- заменяет все директивы `remote` на единый российский relay endpoint;
- сохраняет встроенные CA, сертификат, ключ и TLS-материал;
- при включённом `VPN_BLOCK_IPV6` добавляет блокировку IPv6 до inline-блоков;
- не добавляет клиентские списки доменов или маршруты `net_gateway`.

Решение о российском или зарубежном выходе принимается сервером для каждого IPv4-назначения. Поэтому уже выданные профили без старых статических маршрутов продолжают работать после изменения серверной маршрутизации без перевыпуска.

Имя Telegram-файла очищается от опасных символов. Технический CN и пользовательское имя не смешиваются.

## 8. Пользовательский интерфейс

Middleware при любом обновлении создаёт или обновляет пользователя в БД. Основные возможности:

- главное меню через `/start`;
- список конфигов с пагинацией по 10 записей;
- самостоятельная отправка заявки на новый конфиг без поиска по username;
- признаки срока действия и активного соединения;
- карточка с сервером, датой, загрузкой, отдачей и текущим состоянием;
- скачивание и безопасное переименование;
- перевыпуск активного профиля с выбором целевого сервера;
- получение всех активных файлов одной кнопкой из сообщения рассылки;
- ссылка для оплаты/связи;
- инструкции для iOS, Android и компьютера.

Все основные переходы сделаны inline-кнопками. Текст ожидается только там, где он действительно нужен: поиск, название, дата, реквизиты нового сервера и текст рассылки.

## 9. Административный интерфейс

Администратор определяется точным совпадением Telegram ID из `ADMIN_TELEGRAM_ID`. Ролевой системы с несколькими администраторами сейчас нет.

Админ-панель поддерживает:

- общую статистику пользователей, конфигов и трафика;
- очередь заявок с выбором срока и конкретного готового сервера, одобрением или отказом;
- поиск по username или Telegram ID;
- просмотр пользователя и всех его конфигов;
- выдачу на 30/60/90 дней, 6 месяцев, год или до произвольной даты;
- изменение и продление срока;
- скачивание, перенос и отзыв;
- привязку ранее выданного вручную клиента;
- просмотр серверов, проверки доступности и паузу новой выдачи;
- переименование, добавление и полное удаление сервера с подтверждением;
- массовое продление всех действующих конфигов на 7 дней, 1/3/6 месяцев или год;
- рассылку с предварительным просмотром, сохранением Telegram entities и необязательной кнопкой «Получить все файлы».

Рассылка учитывает Telegram rate limits. Повторная массовая отправка не запускается сама по себе после перезапуска процесса.

При одобрении заявки бот сначала атомарно переводит её в `processing`, создаёт сертификат, а затем одной транзакцией сохраняет `VpnConfig` и состояние `approved`. Ошибка возвращает заявку в очередь и отзывает созданный сертификат. При старте незавершённые `processing`-заявки также возвращаются в `pending`.

## 10. Управление VPN-серверами

### 10.1. Встроенные серверы

Серверы из `NEW_VPN_*` и `OLD_VPN_*` при старте синхронизируются с БД. Для каждого используются отдельный приватный ключ и обязательный SHA256 fingerprint host key.

### 10.2. Выбор сервера

Перед выдачей `ServerManager` берёт только включённые серверы со статусом `ready`, вызывает `list` и пропускает недоступные. Побеждает сервер с наименьшим числом активных клиентов.

### 10.3. Добавление через админку

Администратор вводит название, host, SSH-порт и временный root-пароль. Пароль существует только в памяти текущего процесса и не сохраняется. Бот:

1. создаёт запись `pending`, временно запрещённую для выдачи;
2. подключается по паролю через управляющий SOCKS;
3. устанавливает закреплённую ревизию OpenVPN-install в TCP-режиме;
4. ставит helper, disconnect-hook, пользователя `vpn-bot`, публичный bootstrap-ключ и sudoers;
5. создаёт обратный SSH relay на свободном порту российского сервера;
6. считывает fingerprint и сохраняет отдельный управляющий приватный ключ;
7. проверяет локальный OpenVPN и публичный relay endpoint;
8. переводит запись в `ready`.

Важно: этот автоматический сценарий создаёт автономный OpenVPN на новом VPS и legacy reverse relay. Он не добавляет VPS в схему «OpenVPN в Москве → GeoIP → WireGuard → зарубежный exit». Для нового exit в гибридной схеме нужны отдельные действия из [SERVER_INFRASTRUCTURE.md](SERVER_INFRASTRUCTURE.md).

### 10.4. Удаление сервера

Удаление убирает сервер из пула бота, но намеренно сохраняет связанные `VpnConfig`, `ClientName` и `TrafficEvent`. После удаления исходного VPS такие записи можно перенести на рабочий сервер.

## 11. Привилегированный OpenVPN-helper

Контейнер не получает root и не монтирует PKI. Он подключается к VPN-серверу как `vpn-bot` и может через sudo запустить только `/usr/local/sbin/openvpn-bot-helper` согласно `deploy/sudoers-vpn-bot`.

Поддерживаемые команды helper:

- `create` — создать клиент через EasyRSA;
- `download` — собрать inline-профиль;
- `revoke` — отозвать сертификат и обновить CRL;
- `list` — вернуть известные клиентские CN;
- `stats` — получить серверную статистику;
- `traffic-sessions` — забрать завершённые события;
- `active-sessions` — разобрать OpenVPN status и вернуть текущие подключения.

Helper проверяет формат клиентского имени, исключает серверный сертификат и берёт `flock` с ожиданием до 30 секунд. Это защищает EasyRSA и CRL от параллельной записи.

## 12. Учёт трафика

OpenVPN вызывает `deploy/openvpn-traffic-disconnect` при отключении клиента. Hook записывает завершённую сессию атомарным TSV-файлом в `/var/lib/openvpn-bot/traffic-events`.

Раз в минуту и при ручном открытии общей статистики `TrafficService`:

1. опрашивает доступные серверы;
2. импортирует завершённые события в `TrafficEvent`;
3. повторный импорт игнорируется благодаря составному уникальному ключу;
4. читает OpenVPN status для активных сессий;
5. добавляет текущие байты к исторической сумме только при отображении, не создавая дубликат завершённой сессии.

Все прежние CN остаются связанными с логическим конфигом через `ClientName`, поэтому трафик до перевыпуска не теряется. Глобальная историческая сумма сохраняется даже после удаления конфига или сервера.

Путь `status` в OpenVPN-конфиге должен точно совпадать с путём, который читает helper. Рекомендуемое значение для текущего helper:

```conf
status /run/openvpn-server/server-status.tsv 10
```

## 13. Фоновые задания

| Задание | Период | Поведение |
| --- | --- | --- |
| Напоминания | ежедневно в `REMINDER_HOUR` и при старте | уведомляет за 3, 2 и 1 день; группирует конфиги пользователя |
| Просроченные сертификаты | на 5-й минуте каждого часа и при старте | отзывает сертификат через 24 часа после `expiresAt` |
| Синхронизация трафика | каждую минуту и при старте | импортирует завершённые и читает активные сессии |
| Отложенный отзыв | каждую минуту и при старте | обрабатывает `PendingRevocation`, сохраняет число попыток и ошибку |

`Notification` с уникальной комбинацией конфига, вида сообщения и локальной даты не позволяет повторно отправить одно напоминание. Внутрипроцессные блокировки не дают одному заданию наложиться на предыдущий запуск.

## 14. Отказоустойчивость и консистентность

- Выпуск сертификата компенсируется отзывом, если запись в БД не создалась.
- Перенос откатывается, если старый сертификат не удалось отозвать.
- Пользовательский перевыпуск использует персистентную очередь, поэтому перезапуск не отменяет будущий отзыв.
- Импорт трафика идемпотентен.
- Удаление сервера не каскадирует историю.
- При недоступности одного VPS выдача пробует остальные пригодные серверы.
- PostgreSQL хранится в именованном Docker volume и должен отдельно резервироваться через `pg_dump`.

Бот запускается в одном экземпляре. Внутрипроцессные блокировки не являются распределённой блокировкой; перед горизонтальным масштабированием нужны DB advisory locks или отдельная очередь.

## 15. Безопасность

- Root-пароль нового сервера используется только для bootstrap и не записывается.
- Постоянный доступ выполняется отдельным пользователем `vpn-bot` по ключу.
- Host key проверяется по сохранённому SHA256 fingerprint.
- Привилегии ограничены одной командой sudo.
- Отдельный `vpn-relay` имеет принудительную команду и только разрешённые виды port forwarding.
- Приватные ключи монтируются в контейнер read-only.
- Контейнер приложения работает от непривилегированного пользователя `node`.
- Имена клиентов, названия файлов и пользовательский ввод проверяются.
- `.env`, каталог `secrets`, дампы БД и серверная PKI никогда не коммитятся.

После передачи инфраструктуры следует менять секреты отдельно: Telegram token, пароль БД, relay/bootstrap/control-ключи и root-пароли. Ротация управляющих ключей требует одновременно обновить сервер, Docker secret и соответствующую запись/настройку приложения.

## 16. Разработка и проверки

Локальный минимальный цикл:

```bash
npm install
docker network create vpnbot
docker compose up -d postgres
npm run prisma:migrate:deploy
npm run dev
```

Перед релизом:

```bash
npm test

npm run build
```

Интеграционный PostgreSQL:

```bash
docker compose -f compose.test.yaml up -d --wait
export TEST_DATABASE_URL=postgresql://vpnbot:vpnbot_test@localhost:55432/vpnbot_test
DATABASE_URL="$TEST_DATABASE_URL" npm run prisma:migrate:deploy
npm test
docker compose -f compose.test.yaml down
```

Тесты намеренно выполняются последовательно (`fileParallelism: false`, один worker), чтобы интеграционные сценарии не конфликтовали в общей тестовой БД.

## 17. Как безопасно менять проект

При изменении жизненного цикла конфига нужно одновременно проверить:

1. транзакцию БД и компенсацию внешней операции;
2. CRL на исходном и целевом сервере;
3. связь всех старых CN через `ClientName`;
4. трафик и активную сессию;
5. повтор операции после перезапуска;
6. пользовательский и административный сценарии;
7. миграцию Prisma и обратную совместимость существующих строк.

При добавлении новой команды helper обновляются как минимум сам helper, sudoers при изменении точки входа, парсер в `src/openvpn.ts`, обработка ошибок и тесты. При изменении формата status или traffic event синхронно обновляются серверный hook/helper и `TrafficService`.

## 18. Быстрая диагностика

```bash
# Состояние контейнеров и последние сообщения
docker compose ps
docker compose logs --tail=200 bot

# Применённые миграции
docker compose exec bot npx prisma migrate status

# Доступность helper от имени контейнера
docker compose exec bot sh

# Состояние OpenVPN на точке завершения
systemctl status openvpn-server@server-tcp.service
sudo /usr/local/sbin/openvpn-bot-helper list
sudo /usr/local/sbin/openvpn-bot-helper active-sessions
```

Сначала следует различить три класса проблем: бот не получает Telegram updates, бот не может выполнить управляющий SSH или клиент подключается, но не имеет маршрута в интернет. Для них используются разные SOCKS/SSH, helper и серверная dataplane соответственно.
